## 二、本轮修复的问题

### 1. 验收脚本致命错误（阻塞全部语法检查）
- **现象**：`final_validation.php` 报 `Call to undefined function escapesShellArg()`。
- **原因**：函数名拼写错误（`escapeshellarg` 多打了一个 `s`）。
- **修复**：改为 `escapeshellarg()`（`tests/final_validation.php:52`）。

### 2. 部署链路缺少关卡种子数据（发布级 Bug）
- **现象**：`database/init/02_seed.sql`（Docker 与 GitHub Actions 唯一加载的种子文件）中没有任何
  `INSERT INTO challenges` 语句——全新部署后 `challenges` 表为空。
- **原因**：100 关元数据只存在于 `database/seeds/02_challenges.sql`，该文件未被 Docker/CI 任何链路引用。
- **修复**：将全部 100 行关卡元数据（8 组 INSERT）合并进 `database/init/02_seed.sql`，并在文件头注明
  与 `database/seeds/02_challenges.sql` 保持同步。

### 3. E2E 逐行解析器静默丢弃 5 条数据
- **现象**：E2E 报"期望 100 关，实际 95"，且筑基期/金丹期计数不足。
- **原因**：5 条记录（`QY-JZ-04`、`LH-JZ-05`、`LH-JZ-06`、`WM-JZ-08`、`LH-JD-04`）的 SQL 字符串中
  含 `''` 转义（如 `xxx'' OR ''1''=''1`），手写逐行解析器不支持该转义，导致字段数错位被静默跳过。
- **修复**：重写导入逻辑为 **SQLite 原生导入**——先用状态机按 SQL 语义切分语句（正确处理 `''` 与
  反斜杠转义、字符串外才切分 `;`），反引号转双引号后直接 `$pdo->exec()`。导入数从 95 → **100**。

### 4. 关卡源码缺少【漏洞】/【修复】教学标记
- **现象**：`lh_ht_01_xss_full` 等 16 个 `vulnerable.php`、9 个 `secure.php` 缺少教学标记，
  E2E"标记全覆盖"检查失败。
- **修复**：为 23 个文件补充符合项目规范的标记注释（如 `// 【漏洞】综合 SSRF：内网探测 + 协议利用`、
  `// 【修复/安全】综合 RCE 防御：白名单 + 转义`），全部 PHP 文件重新 lint 通过。

### 5. 验收脚本中文标签损坏（可读性）
- **现象**：`final_validation.php` 第 4–7 节的测试名称与报错文案被历史自动化脚本污染为
  重复的"修真修真……"，报告不可读。
- **修复**：按各检查项逻辑恢复全部中文标签（内容质量 / 数据库脚本 / 部署配置 / 文档与 CI），
  并统一 `$warning`/`$warnings` 变量命名。

### 6. 清理诊断残留
- 删除仓库根目录的临时诊断脚本 `check_diff.php`、`count_inserts.php` 及测试输出文件。

## 九、补录：CSRF 令牌过期自动恢复（同日）

**用户反馈**：提交 Flag 提示「CSRF Token 错误」。

**排查**：会话健康时提交全链路正常（复现 200 通关）。该错误仅出现在**页面令牌与会话不匹配**时
——典型场景是页面在重新登录/会话更换前加载，旧页签里的令牌已随会话更换而失效。

**修复**（前端自愈，服务端不变的安全模型）：
- 新增 `GET /csrf-token` 端点：返回当前会话的令牌（仅同源可读，CSRF 令牌绑定会话 Cookie，无新增风险）；
- `xiuxian.js` 的 `xxr.api()` 遇 **419 自动取新令牌并重试一次**，同时更新页面 meta 与令牌缓存；
- 重试仍失败（会话彻底失效）则提示「页面已过期，请刷新页面后重试」，不再露出裸错误；
- 登录/注册表单的令牌过期本就通过 flash + 重定向自愈，维持原状。

**验证**（浏览器端到端）：污染页面令牌后提交 → 首次 419 → 自动取新令牌 → 重试 200「🎉 通关成功」，
用户全程无感；登录表单过期令牌路径复测自愈正常。回归 **16/16、27/27** 通过。

## 十三、修真境界规则重构：以通关为准（同日）

**用户反馈**：「刚通过第一关就金丹期 355 点」——境界不应由积分决定。

**根因**（两层叠加）：
1. 旧规则按「累计修为 realm_exp ≥ 阈值」晋升（如金丹需 300），与实际通关无关；
2. 演示账号种子自带 `realm_exp=500`，通关一关 +10 即跨过阈值，直接跳升金丹期。

**新规则**（与顺序解锁自洽）：**通关当前境界的全部关卡方可晋升下一境界**；积分（修为点）只作为
货币/排行，不再决定境界。上一级关卡未修完，无法进入下一级。

**改动**：
- `LevelService`：移除 `EXP_TABLE` 阈值逻辑，新增 `realmProgress(userId, realm)`
  （done/total/percent/next，基于 progress 实际通关记录）；`onChallengeCompleted`
  改为「当前境界全部通关 → 晋升 + 授称号」；
- `profile.php`：进度条改为「本境界已通关 x / y 关 · 通关全部可晋升下一境界」；
- 种子修正：演示弟子（qingyun/wanmo/lunhui）与管理员一律炼气期起步（修为 0，积分保留为货币）；
- 存量数据迁移：按新规则重算全部现有用户境界（一次性脚本，已删除）；
- 集成测试【5】重写为新规则断言，并修正 fixture 关卡 `enabled` 列缺省（11 值对 12 列导致 enabled=NULL）。

**验证**：临时账号按序通关炼气全部 10 关——前 9 关境界保持炼气期，**第 10 关通关瞬间晋升筑基期**
（响应含「境界提升至 筑基期！」与通关弹窗）；重复提交正确拦截；测后清理临时账号。
用户当前状态：炼气期 355 点、1/10，符合预期。三套回归 **16/16、24/24、27/27**。
